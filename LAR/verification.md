# Verification Artifacts

**Produced by:** Agent C (Verification Engineer)  
**Independence:** Agent C is on the developer side of the independence line; DO-178C independence comes from the human reviewer at the commit gate, who reviews this verification record. Agent C is blind to Agents A and B's reasoning (anti-anchoring): it receives only formal artifacts — never reasoning or internal deliberation from development agents. If the artifact doesn't demonstrate compliance, it doesn't comply.

**Two kinds of record:** *Tool-produced* records (test results, coverage measurements, static analysis results) carry a verdict from the test framework or analyzer; Agent C only invokes the run, and its opinion never enters the verdict. *Judgment* records (review records, analysis records, problem reports, and the gap dispositions in coverage analysis) are Agent C's draft assessments and are exactly what the human reviewer at the commit gate scrutinizes. Agent C does not sign off on its own verification.

## test_cases/system/ — TC-SYS-XXXX

System-level test cases written against SYS requirements. Verify that the integrated software meets the top-level operational requirements including failure detection and timing.

**File:** `TC-SYS-XXXX-YY.yaml`

```yaml
id: TC-SYS-XXXX-YY
title: [technique — brief description]
requirement: SYS-XXXX
test_level: system
technique: [normal | boundary | equivalence | state_transition | abnormal | failure_condition]
preconditions:
  - [specific system state]
inputs:
  - parameter:
    value:
    unit:
expected_results:
  - parameter:
    value:
    rationale: >
      [traced to requirement text]
pass_fail_criteria: >
  PASS if [specific measurable condition].
  FAIL if [specific measurable condition].
status: draft
```

## test_cases/hlr/ — TC-HLR-XXXX

Integration test cases written against HLR. Written **before Agent B writes code**. The act of writing these tests is the primary mechanism for discovering requirement gaps — when Agent C cannot determine expected behavior for a condition, it generates a Problem Report rather than assuming behavior.

**File:** `TC-HLR-XXXX-YY.yaml` (same format as system test cases above)

---

## test_cases/llr/ — TC-LLR-XXXX

Executable unit test cases written against LLR. These are the tests Agent B must pass. Implemented as pytest test functions with requirement traceability markers.

**File:** `TC-LLR-XXXX-YY.yaml` (YAML spec) + corresponding pytest function in `test_procedures/`

## test_procedures/

Executable implementations of test cases. Python/pytest files. Each test function must include:

```python
@pytest.mark.requirement("LLR-XXXX-YYY")
@pytest.mark.test_id("TC-LLR-XXXX-YY")
def test_[description]():
    """
    Requirement: LLR-XXXX-YYY — [requirement title]
    Inputs: [parameter] = [specific value] [unit]
    Expected: [parameter] == [specific value]
    Pass if: [measurable condition]
    Fail if: [measurable condition]
    """
    # arrange
    # act
    # assert with specific values, not vague conditions
```

## static_analysis/ — SA-XXXX

**File:** `SA-XXXX.yaml`

```yaml
id: SA-XXXX
invoked_by: Agent C
verdict_source: [analyzer and version]
execution_date:
scope: [files or components analyzed]

    violations:

        rule:
        description:
    result: [pass | fail]
result: [pass | fail]
environment:
  software_version:
  compiler:
  target:
status: [pass | fail | blocked]
```

## review_records/ — RR-XXXX

Formal records of every review performed — requirements reviews, architecture reviews, code reviews, test case reviews. Generated by Agent C using Skill 3 (Verification Toolkit, Review mode).

**Authorship:** Agent C's draft assessment. This record is Agent C's judgment, not a tool verdict, and it is reviewed by the human at the commit gate rather than taken on trust.

**File:** `RR-XXXX.yaml`

```yaml
review_id: RR-XXXX
artifact_reviewed: [artifact ID]
artifact_type: [requirement | architecture | code | test_case]
reviewer: Agent C
date:
findings:
  - checklist_item: [R01 | A03 | C02 | T01 | etc.]
    result: [conforming | nonconforming | observation | n/a]
    evidence: >
      [what was examined and what was found]
    problem_report: [PR-XXXX if nonconforming]
summary: >
  [X of Y checklist items conforming. Z nonconformances found.]
recommendation: [approve | revise and re-review]
```

## coverage_analysis/

Structural coverage measurements generated after test execution. The `metrics` are tool-produced: the verdict comes from the coverage tool, not from agent judgment. Agent C drafts the gap categorization and dispositions, which are its judgment and are reviewed by the human at the commit gate rather than taken on trust.

**File:** `COV-XXXX.yaml`

```yaml
analysis_id: COV-XXXX
invoked_by: Agent C
verdict_source: [coverage tool and version]
dal: [A | B | C | D]
metrics:
  statement_coverage:
    achieved:
    target: 100%
  decision_coverage:
    achieved:
    target: 100%
  mcdc_coverage:
    achieved:
    target: 100%
gaps:
  - file:
    line:
    element:
    category: [dead_code | missing_test | deactivated | defensive]
    traces_to: [LLR ID or "none"]
    action:
    disposition: [removed | test_added | justified | pending_human]
status: [complete | gaps_remaining]
```
